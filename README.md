# Meal Planner

Сервис планирования домашнего питания на несколько дней для двух человек. Он должен подбирать порции под цели каждого, учитывать реальные продукты, ограничения и срок хранения еды, а затем сохранять продукты, рецепты и планы для следующих запусков.

## Какую проблему решает проект

Домашнее питание — это не только вопрос «что приготовить». Нужно одновременно решить несколько практических задач:

- уложиться в личные цели по калориям, белкам, жирам и углеводам для каждого человека;
- не использовать аллергены и продукты из личных исключений;
- учитывать доступную кухонную технику и срок безопасного хранения;
- переиспользовать продукты и проверенные рецепты, а не начинать каждый план с нуля;
- следить не только за цифрами, но и за качеством рациона: клетчаткой, солью, сахаром, насыщенными жирами и разнообразием групп продуктов.

Meal Planner собирает эти ограничения в один воспроизводимый план и хранит состояние между запросами.

## Чем это отличается от запроса к ChatGPT или Claude

Обычный чат может предложить меню, но не является источником истины для расчётов и ограничений. Он не обязан помнить точные данные о продуктах, стабильно соблюдать аллергии или одинаково пересчитывать порции.

Языковая модель здесь генерирует только кандидатов новых рецептов, когда в сохранённой библиотеке не хватает подходящих. После этого детерминированный Go-код:

1. проверяет состав и ограничения рецепта;
2. рассчитывает порции и пищевую ценность;
3. выбирает допустимый вариант плана;
4. оценивает качество рациона и объясняет предупреждения.

PostgreSQL хранит продукты, цели, рецепты, планы и историю. Поэтому результат зависит от явных данных и правил, а не от памяти отдельного диалога.

## Текущий статус

Полный путь MVP работает: справочники → генерация плана → список покупок → журнал еды → аналитика.

По HTTP доступны:

- каталог продуктов и ролевых тегов, профили едоков с целями, аллергенами, фиксированными приёмами и исключениями, библиотека рецептов с промоушеном черновиков;
- генерация плана (`POST /plans`) детерминированным солвером с лексикографической целевой функцией, полный план, архивация;
- предпросмотр и применение свопа с blast radius (диффы БЖУ и качества, затронутые приёмы, prep-граф, дельта списка покупок);
- фиксация планового количества продукта с ребалансом долей партии;
- список покупок с сохранением отметок при перегенерации;
- журнал фактической еды, фидбек с ограниченным сдвигом веса ротации;
- аналитика: средние БЖУ, качество рациона с coverage и вердиктами правил, топ рецептов.

Языковая модель подключается опционально: без `LLM_API_KEY` планировщик работает только на сохранённой библиотеке (reuse-only). Когда ключ задан, LLM вызывается только если permanent-кандидатов не хватило или запрошен `novelty_level = 3`, и предлагает только черновики рецептов — валидирует их Go, а выбирает солвер.

Вне MVP остаются Telegram-бот, Mini App, голос, распознавание фото и штрихкодов, синхронизация с FatSecret, учёт запасов, RAG, агенты и дообучение моделей.

## Основные возможности v1

- личная база продуктов с пищевой ценностью конкретных брендов;
- профили двух едоков, цели, аллергии и личные исключения;
- планы на 2–3 дня с отдельными порциями для каждого;
- учёт хранения, оборудования, повторного использования заготовок и ротации рецептов;
- проверка качества рациона и понятные предупреждения;
- список покупок, журнал фактических приёмов пищи и базовая аналитика;
- пополнение библиотеки рецептами от языковой модели только при необходимости.

Эти возможности реализованы и покрыты тестами, включая сквозной smoke-тест всего пути по HTTP.

## Быстрый запуск через Docker Compose

Понадобятся Docker, Docker Compose и Make.

```bash
cp .env.example .env
make up
```

`make up` собирает приложение, поднимает PostgreSQL, применяет миграции и запускает API на `http://localhost:8080`.

Проверить запущенный сервер:

```bash
curl http://localhost:8080/livez
```

Остановить стек:

```bash
make down
```

## Локальная разработка

Для запуска Go-приложения вне контейнера нужны Go 1.27, Make и доступный PostgreSQL.

```bash
cp .env.example .env
docker compose up -d postgres
make generate
make migrate
make run
```

Основные команды:

```bash
make help              # показать все цели
make generate          # сгенерировать код из SQL и OpenAPI
make build             # собрать bin/server
make run               # запустить cmd/api
make migrate           # применить миграции
make migrate-status    # показать статус миграций
make seed              # загрузить локальные демо-данные
make test-unit         # запустить модульные тесты
make test-integration  # запустить тесты с PostgreSQL
make test              # модульные и, при настройке, интеграционные тесты
make lint              # запустить golangci-lint
make tidy              # привести go.mod и go.sum в соответствие с кодом
```

## Демо-данные для локальной разработки

`make seed` загружает `migrations/seed/dev_seed.sql`: двух едоков с разными целями,
аллергеном и жёстким исключением, фиксированный завтрак, набор продуктов с
намеренно разной полнотой данных о нутриентах и пять permanent-рецептов. Этого
достаточно, чтобы сгенерировать план и увидеть как предупреждения качества, так и
статусы `unknown` при неполных данных.

Сид — данные разработки, а не миграция: он идемпотентен и не должен применяться к
базе с реальной историей планирования.

```bash
export DATABASE_URL=postgres://postgres:postgres@localhost:5432/meal_planner?sslmode=disable
make migrate
make seed
```

`make test-integration` требует `TEST_DATABASE_URL` с отдельной тестовой базой. Настройки и примеры значений находятся в `.env.example`.

## Архитектура в двух словах

Проект — модульный монолит: одно Go-приложение, разделённое на модули по предметным областям, и одна база данных PostgreSQL.

- Внутри — правила продуктов, едоков, рецептов и планов, детерминированный подбор плана и проверка качества рациона.
- Снаружи — HTTP, OpenAPI, PostgreSQL, сгенерированный SQL-код и провайдеры языковых моделей.
- Внешние детали зависят от внутренних правил, но внутренние правила не зависят от HTTP, базы данных или SDK провайдера.
- Языковая модель предлагает только кандидатов рецептов. Go проверяет их, а итоговое решение принимает солвер.

Поэтому бизнес-правила тестируются без сети, базы данных и внешней модели.

## Границы проекта

Это личный проект для одного домохозяйства из двух человек, а не многопользовательский сервис. В v1 доступен только HTTP API со статическим токеном `X-API-Token`.

Telegram-бот, мини-приложение Telegram, голосовой и визуальный ввод, сканирование штрихкодов, учёт запасов, автономные агенты и другие внешние интеграции не входят в v1.
