# Agent Notes

This is an owner-only Go modular monolith for meal planning, not a SaaS platform and not a microservice system. Keep the implementation boring, explicit, and close to the current MVP scope.

Architecture: **domain-first modular monolith + DDD-lite + ports/adapters**. Use Clean Architecture as a dependency rule, not as boilerplate folder ceremony.

Read these before making structural changes:

- `docs/DESIGN.md`
- `docs/SPEC.md`
- `docs/ARCHITECTURE.md`
- `docs/schema.sql`
- `api/openapi.yaml`

Core rules:

- HTTP, OpenAPI, Postgres, sqlc and LLM providers are adapters.
- Solver, quality rules, plan generation, recipe slots and macro logic are core.
- Core packages must not import HTTP handlers, OpenAPI DTOs, sqlc rows, Postgres repositories or provider SDKs.
- LLM only generates recipe candidates. Go validates them, the solver decides whether to use them, and the quality evaluator explains the result.
- Prefer small Go packages with domain names over generic folders like `services`, `utils`, `common`, `interfaces`.
- Put interfaces on the consumer side, usually in `usecase/*/ports.go`.
- Do not invent fields or endpoints. `docs/schema.sql` and `api/openapi.yaml` are the source of truth.
- Keep v1 scope: HTTP API only. Telegram bot, Mini App, voice, vision/barcode, FatSecret sync, inventory, RAG, agents and fine-tuning are v2+ or explicitly out of scope.
- Comments must justify a non-obvious invariant or decision. Do not add AI-style narration, restate code, or comment routine control flow.
- OpenAPI handlers return generated strict response objects or errors. Keep error-to-HTTP mapping in the HTTP adapter; do not hand-roll successful JSON responses.
- Use GoMock generated by the pinned `mockgen`; do not write fake, stub, or mock implementations by hand.
- Configure `slog.Default()` once in `cmd/api`; do not inject or store loggers in application structs.
- Apply KISS and Pareto: add an abstraction only for a current repeated need, not for hypothetical reuse.

Agent workflow:

- When the owner corrects behavior that can recur, distill it into one concise, enforceable rule here. Do not paste chat history or task-specific acceptance criteria.
- Do not create or commit agent-generated plans or specs unless the owner explicitly requests them. Keep working plans in task state.
- Work in the current checkout and feature branch. Do not create or use Git worktrees unless the owner explicitly asks for one.

HTTP and OpenAPI:

- Keep OpenAPI-to-usecase and domain-to-OpenAPI mappings in a dedicated mapping file or type. Handlers should only map input, call a use case, and return a generated response object or error.
- Do not wrap generated strict responses in generic writers, visitor callbacks, `writeOpenAPIResponse`, or manual success writers such as `respondJSON`.
- Do not add `501 Not Implemented` placeholder handlers or per-handler nil checks for required dependencies. Required dependencies belong in the composition root.
- Do not add full generated-server conformance assertions solely to force placeholder methods.
- Do not swallow errors. Preserve typed application errors for centralized HTTP mapping; wrap only when the added operational context is useful and `errors.Is`/`errors.As` still work.

Testing:

- For mechanical CRUD, test the failure boundaries that can realistically break: mapping and validation, application-error mapping, and transaction or adapter behavior. Do not duplicate every handler, status, or success path and do not default to exhaustive TDD.
- Keep adapter integration tests beside the adapter under an `integration` build tag. Reserve `tests/integration` for cross-adapter or full-stack workflows.

Git conventions:

- Commits follow **Conventional Commits**: `type(scope): summary` (e.g. `feat(planning): reuse-first plan generation`). Types: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `perf`, `build`, `ci`.
- Branches mirror the commit type: `type/short-description`, kebab-case, e.g. `feat/eater-exclusions`; prefix the issue number when there is one: `feat/42-generate-plan`.
- PR descriptions include a separate `Closes #N` line for every issue fully implemented by the branch.

When unsure, choose the simplest implementation that preserves the important boundary: **deterministic Go core first, external adapters second**.
