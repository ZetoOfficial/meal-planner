# README Redesign

## Цель

README должен за две-три минуты объяснять новому читателю, какую проблему решает проект, чем он отличается от обычного запроса к ChatGPT или Claude, насколько проект готов и как его запустить.

## Аудитория

Основная аудитория — разработчик, впервые открывший репозиторий. README не должен быть внутренней памяткой владельца проекта или полной копией продуктовой и архитектурной документации.

## Позиционирование

Meal Planner — сервис для планирования домашнего питания на несколько дней для двух человек. Он рассчитывает порции под цели каждого человека и учитывает реальные продукты, аллергии, личные исключения, хранение, кухонную технику и качество рациона.

Главное отличие от обычного чата: искусственный интеллект может предложить новый рецепт, но ограничения, расчёты и проверки выполняет детерминированный Go-код. Результат можно проверить, объяснить и повторно рассчитать, а продукты, цели, рецепты и планы сохраняются между запросами.

## Структура

README состоит из следующих разделов:

1. Название и краткое описание продукта.
2. Проблема, которую решает проект.
3. Главное отличие от обычного чата.
4. Основные возможности.
5. Честный текущий статус.
6. Быстрый запуск через Docker Compose.
7. Локальная разработка и основные команды.
8. Краткое описание архитектурных границ.
9. Карта подробной документации.
10. Явные границы проекта: owner-only HTTP API, не SaaS.

## Язык

Основной текст пишется по-русски простыми словами. Английские термины используются только для имён технологий, команд, файлов и общепринятых обозначений. `Meal-prep`, `solver`, `quality evaluator` и `LLM` не используются без необходимости и пояснения.

## Сокращение текущего README

Из README удаляются:

- подробная таблица всех переменных окружения;
- рабочие заметки по реализации;
- полный список архитектурных правил;
- фиктивный пример запроса на несуществующий маршрут;
- подробности, уже описанные в `docs/DESIGN.md`, `docs/SPEC.md` и `docs/ARCHITECTURE.md`.

README сохраняет только минимальные сведения, необходимые для знакомства с проектом, запуска и навигации по документации.

## Точность статуса

Описание возможностей отделяется от текущего состояния реализации. README не должен создавать впечатление, что продуктовая логика уже готова, если в репозитории реализована только инфраструктурная основа.

## Проверка

После изменения необходимо проверить:

- соответствие команд актуальному `Makefile`;
- соответствие запуска `compose.yaml` и `.env.example`;
- существование всех ссылок на файлы;
- отсутствие устаревших упоминаний readiness, заглушек и несуществующих маршрутов;
- корректность Markdown через `git diff --check`.
